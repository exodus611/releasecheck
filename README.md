# releasecheck — preflight checks for a release folder

**Check before you send.** Point it at the folder you are about to hand to someone —
a store, a printer, a client, a colleague — and get one verdict: **PASS** or **FAIL**,
with reasons.

[![ci](https://github.com/exodus611/releasecheck/actions/workflows/ci.yml/badge.svg)](https://github.com/exodus611/releasecheck/actions/workflows/ci.yml)

```
git clone <this repository> && cd releasecheck
python3 demo/make_fixtures.py               # builds two demo folders, no network needed
python3 releasecheck.py check demo/_build/good    # PASS
python3 releasecheck.py check demo/_build/broken  # FAIL, with 12 realistic reasons
```

No installation. No dependencies. Python 3.9+ and the standard library. Nothing is
uploaded anywhere, and no network call happens unless you pass `--online`.

Use it in your own repository as a GitHub Action:

```yaml
- uses: exodus611/releasecheck@main
  with:
    folder: dist
```

## Who this is for

Anyone who ever sent a folder of files and hoped it was fine:

- **writers and small publishers** — the manuscript package that goes to a store
- **freelancers** — the deliverable bundle that goes to a client
- **designers and photographers** — the export folder where one image is broken,
  the wrong size, or a duplicate under another name
- **developers** — the release archive with a stale file, a leftover build, or a key
  that got pasted into a config an hour before shipping
- **anyone who works from a phone** — one command, one verdict, no laptop session

The point is not to replace a proofreader or a print proof. The point is that the
mechanical part of "is this package clean?" should not depend on your memory at
11 p.m. the night before you send it.

## What it checks

| Check | What it catches |
|---|---|
| files | empty files, desktop junk (`.DS_Store`, `Thumbs.db`, `__MACOSX`), files matching a forbidden pattern, stale files that are not part of this release |
| duplicates | the same bytes shipped twice under two different names |
| archives | corrupt or truncated archives, CRC failures, encrypted members, unsafe member paths (zip-slip), epub `mimetype` rules, docx required members |
| metadata | an epub missing title, author, language or identifier in its OPF |
| secrets | private key blocks, provider tokens and assigned secrets such as `api_key = "…"` — **including text inside docx, epub and zip archives**; matches are masked, never printed |
| placeholders | `TODO`, `FIXME`, `TBD`, lorem ipsum, `REPLACE_ME`, unfilled `{{template}}` markers in the text you are about to ship |
| hashes | files that changed after the hash list was written, missing files, archives not covered by the list |
| images | images below a required size (for example a cover), unreadable image headers |
| pdf | a broken header, a missing `%%EOF` (truncated file), an encryption entry that stores reject |
| links | relative links pointing nowhere, plus optional external link checks with `--online` |

Every report ends with **what the check does not prove**. That block is part of the
design, not a disclaimer afterthought.

## Exit codes

`0` PASS · `1` FAIL · `2` bad usage. Drop it into CI and the build stops when the
release folder is not clean:

```yaml
- name: Preflight the release folder
  run: python3 releasecheck.py check dist -m releasecheck.json --json report.json --md report.md
```

The markdown report is written for pull requests and release notes; the JSON one is
for machines.

## Configuration (`releasecheck.json`, optional)

```json
{
  "name": "my release 1.2",
  "artifacts": ["book.epub", "book.pdf", "cover.jpg"],
  "images": [{"path": "cover.jpg", "min_long_side": 1600}],
  "forbid": ["*.key", ".env", "*.bak"],
  "hashes": "SHA256SUMS.txt",
  "online_links": false,
  "ignore": ["private-notes.md"]
}
```

Without a manifest the tool still runs and checks every file it finds. See
`releasecheck.example.json`.

## What it does not prove

- that a store, a printer or a client will accept the files;
- that the content is true, legally safe, or free of third-party rights;
- **that your Git history is clean** — a secret committed and later deleted still
  lives there. This tool reads the folder, not the history, and says so;
- that a human read the result, or that anyone wants it.

## Status

`0.1.0` — a working prototype, tested. 11 unit tests cover the checks that matter:
zip-slip rejection, secrets inside archives, stale hashes, epub packaging rules,
truncated PDFs, image sizing, offline behaviour and exit codes. Test data is
generated by the repository itself, so the tests need no network and no fixtures
with real secrets in them.

Known limits, stated honestly: the PDF page count is approximate; image checks read
headers and do not decode pixels; the external validator for epub quality is not
bundled (the structural checks here are not a substitute for a full validator).

## Roadmap (each item is a check + a test + a row in the table above)

- read the **Git history** — a secret committed and later deleted is still there;
- exact PDF page count and print-block geometry instead of an approximation;
- an optional external epub validator, reported honestly when it is not installed;
- print profiles: margins, bleed, spine width, cover resolution;
- rights and licences: does every font and image in the package carry its licence?

Issues labelled `good first issue` are open for anyone.
